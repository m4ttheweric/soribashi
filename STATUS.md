## Toast: the manager-driven capstone recipe, §11 roadmap complete (2026-08-27)

Toast was the one unbuilt entry on the parent spec's §11 component roadmap (`.local-dev/specs/2026-07-24-soribashi-ui-design.md`), chosen to prove an imperative/programmatic API, a surface nothing else in the package touches. The July roadmap assumed it would need hand-rolling because Base UI lacked the primitive; that was stale by build time (installed `@base-ui/react@1.6.0` ships a full `toast` primitive), so Toast became a category-2 wrap plus a new manager layer. **`@soribashi/ui` now has 29 recipes, and the §11 roadmap is complete.** Branch `feat/toast-recipe`, from `main` @ `fafb2d9`, 7 commits (spec → subagent spec-review → plan → inline TDD execution, four tasks → whole-branch review → one fix wave), fast-forward merged at `97f74f1`. Spec + plan (gitignored) at `.local-dev/specs/2026-08-27-toast-recipe-design.md` and `.local-dev/plans/2026-08-27-toast-recipe.md`; outcomes at `.local-dev/toast-outcomes.md`.

### What landed

- **A `defineCompound` with a global Provider and an imperative queue.** `Toast.Provider` IS the compound's `parts.root` (the one architecture that works: a Viewport rendered outside a compound root would hit `rawCtx === null` and `getStyles('viewport')` would throw). `Toast.Viewport` is batteries-included: it wraps Base UI's `Portal` + `Viewport` and owns the `manager.toasts.map(...)` itself (Base UI's own Viewport renders only children + focus guards + a hidden live region). The per-instance anatomy (`toast`/`title`/`description`/`close`/`action`) are **style slots, not parts**, addressed via `getStyles({ part })` in the map, so the public surface stays `Toast.Provider` + `Toast.Viewport` (no `Toast.Toast`).
- **Per-toast dynamic intent coloring.** Intent is set imperatively (`useToast().add({ intent })` maps to Base UI's per-toast `type`), so it cannot ride the static vocabulary-axis path. The Viewport map computes `autoVars(theme, 'Toast', { intent: t.type, variant: ctx.variant }, true)` per toast (gated on `t.type`, else the neutral `--surface-raised` CSS fallback) and spreads it inline. Colour comes only from the theme's intent resolver (invariant 2 intact); `intent` stays typed `string` (a vendored recipe has no opinion on vocabulary values). Variants `filled`/`light`/`outline`, default `light`, are the static axis. 18 contrast cells (6 intents x 3 variants) clear AA in both schemes.
- **The `useToast()` wrapper** (intent→`type`, action→`actionProps`) plus a `createToastManager` re-export for enqueuing outside React. Enter/exit motion rides the `--motion-*` tokens (the migration that landed in the debt sweep). Full recipe-contract registration; authoring skill gained **§23** documenting the manager-driven sub-pattern and its traps.

## The design ledger: named design decisions gated in CI, and the eight-defect sweep that produced it (2026-08-03)

Slice 4 (below) closed at 28 recipes with every gate green. A single unhurried walk through `apps/workshop` then produced eight visual defects in a row: the vertical Tabs indicator anchored to the wrong block edge, the Select popup rendering over its own trigger, the Switch thumb off-centre, the RadioGroup dot landing on half pixels, the Tooltip apparently dead, the Accordion not animating, Skeletons too faint to read as absent content, and a Dialog scrim reported as opaque. Seven were real. That ratio, eight findings from one human eyeball against a fully green suite, is the actual subject of this branch: the gates could tell whether a component was *correct*, and had nothing to say about whether it looked *right*.

The answer is a **design ledger**: a table of named numeric decisions, each asserted in a test against real rendered geometry or colour, with an external library (shadcn, pinned by version and commit) admitted as **evidence and never as authority**. Branch `feat/design-ledger`, from `main` @ `af605d6`, 28 commits, executed subagent-driven across 11 planned tasks plus a whole-branch review, one fix wave, and two user-reported follow-ups.

### What landed

- **The ledger itself (`packages/ui/src/design-ledger/`), 10 rows over three species.** `species: 'floor'` is a perceptual bound where an outside library's value is cited as corroboration, not as the source of truth; `species: 'identity'` is soribashi's own recorded decision, which may carry no external witness at all; `species: 'invariant'` is a structural truth with no external value to compare against (a thumb is centred or it is not). `validateLedger()` enforces the species rules, and a row that wants to depart from its witness must fill `diverge` with a `proof-via:` pointer at a proof, never with a reason. Shipped rows: 7 invariant (`switch.thumb.centered`, `switch.trackWidth.wholePixel`, `radio.dot.centered`, `tabs.indicator.withinList`, `select.popup.clearsTrigger`, `focus.ring.uniform`, `controls.sharedHeight`) and 3 floor (`dialog.scrim.effectiveDarkness`, `skeleton.deltaY.light`, `skeleton.deltaY.dark`). No identity rows yet, deliberately (see below).
- **Two rules that keep the table from becoming decoration.** *Scope*: every row gates the shipped `uiTheme` only, never a consumer theme, so the ledger can hold an opinion without the framework holding one (CLAUDE.md invariant 2 survives intact). *Admission*: a row must trace to an observed defect, not to a category of possible defect. `controls.sharedHeight` is the one row admitted on argument instead, and says so in its own comment.
- **`coverageReport()` prints on every run, so green never reads as complete.** The current line is `design ledger: 10/10 rows declared / covering 12 of 28 recipes / uncovered: AspectRatio, Avatar, Badge, Box, Center, Container, Divider, Field, Grid, Group, Paper, Popover, Stack, Text, Title, Tooltip`. A pass count alone would read as "swept"; naming the 16 recipes nothing looked at keeps "no known defect" distinct from "checked".
- **Seven defects fixed, each traced to a cause rather than nudged until it looked right.** Tabs: the base rule's `inset-block-end: 0` survived into the vertical override, so the indicator was anchored to both block edges at once. Switch: the thumb was positioned against the padding box (already inset by the 1px border) but sized as if against the border box. RadioGroup: 50% of the content box gives symmetric but half-pixel gaps at sm (4.5) and lg (5.5) only. Select: Base UI's `alignItemWithTrigger` defaults to `true`. Focus rings: five recipes carried divergent fallbacks for `--accent-primary`, a property no theme in this repo emits. Skeleton: `--surface-raised` sits one ramp step from the canvas, far too close for a placeholder. Tooltip: not broken at all, just Base UI's 600ms default delay, though its `.trigger` separately had no CSS rule so `getStyles()` returned `''`. The eighth, the "opaque" Dialog scrim, **did not reproduce**: one backdrop, alpha 0.6, clean ancestor chain. It is recorded as a floor row anyway (`dialog.scrim.effectiveDarkness`, measured 0.476 inside [0.4, 0.7]) so a future regression has something to fail against.
- **Motion tokens, and the Accordion animation they unblocked.** `motionDuration` (`fast`/`base`/`slow`) and `motionEase` (`enter`/`exit`/`standard`) join the theme as first-class families, emitted by codegen with a reduced-motion collapse to `0.01ms` rather than `0`, deliberately, so `transitionend`/`animationend` still fire and nothing that awaits them hangs. Accordion's panel then needed three things together: `keepMounted: true` (Base UI's own default is `false`, and a panel that unmounts leaves nothing to animate), keyframes rather than a transition (a closed panel is `hidden`, so `display: none`, and a transition cannot interpolate out of it), and the panel's padding moved into a new `panelContent` slot. That last one is the non-obvious part: Base UI reports `--accordion-panel-height` as the *content* height (18px) when opening and the *full* height (30px) when closing, so while padding sat on the animated box no single `box-sizing` choice was correct in both directions, and the panel visibly jittered. With exactly one property animating, both directions are clean. Verified live in the running workshop at this HEAD by sampling the panel's measured height on every animation frame (values below are every second sample): open `[0, 13.72, 27.63, 30, 30]`, close `[30, 22.94, 4.23, 0.11, 0]`. Both monotonic, peak equal to final, overshoot 0. Also captured as slow-motion frame strips in both directions and read back as images, since a number that is monotonic can still look wrong.
- **A framework capability, added rather than worked around.** Skeleton needed different neutral ramp positions per colour scheme, and the first fix reached for `:global(.dark) .root`, the only such rule in any recipe, which would have baked a scheme choice into recipe source and broken the roadmap's "fully re-skinnable through `createTheme` plus `.extend()` alone" criterion. Instead `SemanticSurfaceValue`'s object form gained an optional per-scheme `dark` reference, resolved through codegen's existing `pairValue` into a single `light-dark()` custom property. Skeleton is scheme-blind again: one `background: var(--surface-placeholder)`. The nested `light-dark()` this produces is safe for a specific reason the review verified rather than assumed: colour custom properties are *unregistered* (`emit-property.ts` registers only radius/spacing/fontSize), so both levels resolve against the same element's used `color-scheme` and cannot disagree. Registering them would break it.
- **The whole-branch review found one critical the branch had introduced itself.** `--surface-placeholder` was declared only in `packages/ui/src/theme.ts`, never in `DEFAULT_SURFACE`, so Skeleton rendered **fully transparent under every theme except `uiTheme`**, including the starter `soribashi-init.json` scaffolds. Three gates were each blind to it from a different angle: `token-existence.test.ts` checked `emitCss(uiTheme)` only; `reskin.test.tsx` asserts that at least one property *differs*, and a token vanishing is a difference; Skeleton is not in `SMOKE_ITEMS`. Fixed by moving the default into `DEFAULT_SURFACE` (retyped to `Record<string, SemanticSurfaceValue>`), plus a new gate that checks every recipe's `tokenDependencies` against what a *bare* `createTheme` emits, with an allowlist that is empty by measurement.

## Key wins from the design that landed

- **Theme is the contract**: every component accesses tokens through `theme`; codegen ensures Tailwind config matches.
- **`defineComponent({...})`**: single config object, types inferred. The `Button` component implementation in `apps/playground/src/components/Button/Button.tsx` is ~70 lines (vs Mantine's ~280 for the equivalent).
- **Auto-vars for intent × variant**: components declaring `variants` automatically get `--{name}-bg/-color/-border/-hover/-active` on root via the theme's `intentResolver`. No manual `varsResolver` needed for the standard case.
- **Surface elevation** as first-class: `bg="raised"` etc. resolves to `var(--surface-raised)`. Avoids the Mantine workaround documented in console-archive (manual `--mantine-color-background-1..4` injection).
- **Substrate-agnostic styling**: `defineComponent` accepts CSS module classes, Tailwind/CVA recipes, or plain class names. `Button` uses plain CSS that references `var(--button-bg)` etc.
- **Layered token composition**: `createTheme({ extends: baseTheme, ... })` works; tested in roundtrip.
- **Generic component support**: `defineGenericComponent<SelectOwnProps<T>>` preserves the type parameter.
- **Polymorphic component support**: `definePolymorphicComponent` with `as` prop; `Box`, `Text` use it.
- **Codegen drift impossible**: Tailwind config is generated from the theme; you cannot reference a token that doesn't exist.
